    Phase 7: optional existing AKS and ACR

    Phase 7: application-only preparation for existing AKS/ACR. Required real inputs, current trusted main, same-run immutable digests and independent live-verifiable approval are non-negotiable.

    Not rehearsed⏱ Separate optional operation; independent approval waits unknown$ Existing resources plus image builds/storage/runners/network may billWorkstation showcase

    Copy-only instructions. Checkmarks are manual progress, not laptop verification.

    $
    This page starts something that bills. Only a separately authorized human can perform these actions. Read the prerequisites and independent approval gates first. This HTML never dispatches or deploys.

    ✎ Your values for this page

    The commands below contain values only you know. They are highlighted. Type them once here and every command on this page fills in, and so do the commands on the other pages of this guide that you open in this browser tab. Only the non-sensitive reviewed main SHA is accepted, kept in this tab session only and never sent anywhere. Browser session restore may retain it. Never enter credentials or customer data.

    APurpose and place in the demo

    Explain a protected existing-infrastructure delivery path without silently provisioning or authenticating to finish a preparation exercise.

    Agents may prepare/review files only. No cluster/registry/namespace/RBAC/ingress creation, Azure sign-in, image build/push, kubeconfig retrieval, dispatch or deployment by an agent.

    BStarting state

    IT owns existing AKS/ACR, a precreated restricted namespace, approved build/deploy identities, kubelet pull permissions, runner network/tool readiness and supported GitHub environment protections.

    F
    Field note cloud · Existing infrastructure only

    Existing AKS/ACR, real inputs, trusted current main, same-run immutable digests and independently verified environment approval are required. Unavailable or unverifiable protections fail closed.

    Source-bound operating boundary; not a laptop observation.

    CExact actions

    1. YYou / IT

      Require real existing-resource and image inputs

      Repository Settings›Secrets and variables›Actions›Variables

      Required variablesMeaning; no example values
      AZURE_BUILD_CLIENT_ID / AZURE_DEPLOY_CLIENT_IDDistinct build/push and namespace-deploy identities
      AZURE_TENANT_ID / AZURE_SUBSCRIPTION_IDApproved existing target; identifiers are not passwords
      ACR_NAME / AKS_RESOURCE_GROUP / AKS_CLUSTER_NAMEExisting approved registry and cluster
      AKS_NAMESPACEExisting precreated restricted namespace
      AKS_RUNNER_LABELS_JSONApproved connected equipped Linux deployment runner labels
      Optional ACR_RUNNER_LABELS_JSONApproved equipped Linux image-build runner for restricted ACR when needed

      Application namespace/images remain required inputs with no placeholder/default demo images or latest tags. Deployment consumes immutable digests produced by its own run, not a hand-entered mutable tag. Do not collect these values or secrets in this HTML.

      No client secrets, AZURE_CREDENTIALS, registry passwords, access tokens or admin kubeconfig. Reverify actual immutable OIDC subject format/ref/environment with IT; old/widened/wildcard trust is not recovery.

      You should see

      Real approved prerequisites or explicit unset inputs; no provisioning to make the plan look complete.

    2. AAgent: scoped files

      Prepare/review application objects and static gates only

      k8s\workloads.json›Kubernetes manifest check

      Review required namespace/digest inputs, non-root Deployments, health probes, requests/limits and ClusterIP Services. Existing templates also restrict capabilities, root filesystem, seccomp and service-account token use. Static checks do not fill missing inputs or prove a live cluster.

      Use existing dependencies only. No authentication, tool acquisition, image build/publish, namespace creation, public ingress, firewall change or cloud dispatch.

      You should see

      Static file evidence, real missing inputs and unobserved live checks explicitly separated.

    3. YYou / IT

      Verify actual independent environment protections

      GitHub Settings›Environments›aks-demo

      • Required reviewer independent of initiator.
      • Prevent self-review enabled; administrators cannot bypass protection.
      • Selected branches/tags: exactly one Branch rule for main; no tag/wildcard/PR rule.
      • Protect trusted main and workflow/checker/manifests through governance; editable YAML alone is not an independent boundary.
      ✕

      Private environment creation is not proof of reviewer support. Use a compatible GitHub plan and verify actual live REST protections/readability. If controls are unavailable, absent or unverifiable, fail closed: no bare-dispatch downgrade, extra long-lived token workaround or visibility change.

      You should see

      Verified live protection and independent reviewer evidence, not a claim based only on a named environment.

    4. GGitHub Actions

      Trust current main, exact source SHA and modern CI

      Reviewed main›deploy-aks.yml governance/tests

      Manual workflow_dispatch only on trusted main. Required source_sha must equal the dispatch revision and current remote main. If main moves, stop and start a new reviewed run; this guide's dated pin and demo-complete are not dispatch inputs.

      Modern Python/current Java/Go and repository checks precede separate OIDC registry build/push. Same-run immutable digests pass through job outputs; distinct deploy identity cannot use a mutable tag or unrelated digest.

      IT verifies ACR mode: non-ABAC AcrPush/AcrPull vs ABAC repository-scoped Writer/Reader, conditional permissions and separately justified catalog/read scope. Kubelet pulls images; no attach-acr/role grant or broad Contributor/Owner workaround.

      You should see

      Exact current-main test/digest/governance evidence or a fail-closed stop.

    5. YYou / IT

      Only an authorized human requests and monitors deployment

      Terminal›Run Task›Deploy AKS (manual main only)

      Only after prerequisites and live protections are verified, the human supplies the reviewed current full main SHA to the actual named task and explicitly confirms. The optional code below remains visibly unresolved until a valid SHA is entered; copy never dispatches.

      Dispatch is a request, not environment approval. A different approved reviewer uses Review deployments: aks-demo. Protections/source are rechecked before Azure OIDC; the deploy identity uses user, never admin, kubeconfig and Entra kubelogin in the existing namespace.

      Already equipped connected Linux runners are required; labels alone do not prove API/DNS/TLS/ACR/identity reachability. Never make a private API public, disable validation, install runner tools or grant admin credentials to fix a run.

      Open CI and manual workflow runs ↗
      You should see

      An actual independent approval and rollout/health result, or a truthful wait/failure. No live action is performed by HTML/agent.

    6. YYou / IT

      Inspect namespace-scoped status, logs and loopback access

      Terminal›Kubernetes status / Kubernetes logs / Kubernetes port-forward

      Use already approved local user kubeconfig/network context, the actual existing namespace and the selected modern sample. No task should acquire admin credentials, create namespace/RBAC or expose public ingress.

      Port-forward occupies its integrated terminal and uses loopback; human stops only that owned operation with Ctrl+C and uses a second terminal for health/synthetic requests. Inspect actual rollout/probe/health evidence, never assume a past deployment.

      You should see

      Observed namespace-scoped outcomes or NOT RUN. Existing Azure resources keep their normal costs; this plan never deletes them.

    EExpected result

    Files-only preparation may be complete while cloud deployment is not authorized or available. A real accepted delivery requires current-main tests, same-run image digests, independent approval and observed rollout/health.

    FVerify and recover

    How to confirm success

    Observe live governance/source checks, modern CI, distinct identity scopes, same-run registry digests, independent reviewer and actual rollout/health. None is inferred from static files or a dispatched workflow.

    If something goes wrong

    Reviewer protections unavailable/unreadableDo not repeat
    Likely cause
    Private-plan limitation, missing controls or insufficient live verification
    What to do
    Fail closed and do not deploy. Obtain independently verifiable supported protection through approved administration; no visibility/token/admin bypass.
    Current main moved or digests do not match this runDo not repeat
    Likely cause
    Stale source input or mutable/unrelated image identity
    What to do
    Stop and request a new separately reviewed current-main run; never deploy fallback/tag/PR/legacy code.
    Missing variables/namespace/tools/RBAC or private API reachabilityDo not repeat
    Likely cause
    Existing infrastructure/runner prerequisite is unmet
    What to do
    Report the exact missing input/check NOT RUN; do not authenticate, provision, grant rights, fetch tools or open networks to finish prep.
    Rollout/probe/health failed after approved deliveryRepeat with care
    Likely cause
    Application/runtime/image/resource issue
    What to do
    Stop acceptance and inspect authorized namespace evidence; no unrelated resource deletion or unsafe baseline recovery.

    Safe recovery

    Retain existing cloud resources and all source. Re-review a new current-main run only after the real blocker is resolved through authorized human/IT processes.

    Limits of this check

    No Azure authentication, live cluster inspection, image publication, dispatch, reviewer approval or deployment was observed/performed by this companion.
