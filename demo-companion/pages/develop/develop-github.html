    Developer workflow

    Phase 6: GitHub review and exact-SHA CI

    Phase 6: sign-in, scoped file work, commit/publish, PR review and exact-SHA CI are distinct decisions. Push/PR never deploys.

    Documented⏱ Review and hosted checks are variable$ Approved private GitHub/Copilot accessWorkstation showcase

    Copy-only instructions. Checkmarks are manual progress, not laptop verification.

    APurpose and place in the demo

    Create a small reviewable change with actual validation evidence and preserve unrelated source/session work.

    Agent/customization/tool availability is not permission to sign in, publish, repair the machine or dispatch Actions.

    BStarting state

    Human-approved GitHub sign-in, required private write access/Copilot entitlement, safe reviewed checkout and already available dependencies. No competing setup/app/Restore tasks.

    CExact actions

    1. YYou / IT

      Confirm GitHub and Copilot access separately

      VS Code›Source Control / GitHub Pull Requests view

      Use existing approved access and account/profile routing. Setup and Verify do not sign you in or accept a seat. Do not bypass corporate policy, switch accounts/sources unexpectedly or add tokens to HTML/source.

      You should see

      Actual authorized access or an explicit blocker; workflow status does not repair or authenticate.

    2. YYou / IT

      Inspect a focused diff and explicitly choose publication

      Source Control›Stage intended files›Commit›Publish Branch

      1. Read applicable instructions/sample README and make only requested synthetic file changes.
      2. Inspect diff and run the relevant existing no-restore checks; preserve unrelated staged/unstaged/untracked/unsaved work.
      3. Only if authorized, stage intended files, use a conventional commit and Publish Branch. Branch/commit/publish are not setup permissions.
      4. If a PR is requested, use GitHub Pull Requests: Create Pull Request, preserving repository template sections/checklists and exact observed commands/results/skips.
      You should see

      A small intended review surface with genuine results, not a blanket stage/commit or invented passing evidence.

    3. GGitHub Actions

      Read every exact-SHA modern-service job and artifact

      GitHub Pull Requests›Checks / Actions›Exact revision

      Normal CI covers Python, current Java, Go, PowerShell 5.1 and 7, repository/config checks and three modern container build jobs. Legacy Java 11/Boot 2.7 is excluded.

      Observe actual job statuses/results on the intended commit, not a stale branch label or top-level run alone. Review reports/artifacts. A successful hosted container build is not a local launch or AKS deployment.

      Merge/review of main and optional existing-AKS dispatch/independent approval are separate decisions. A PR/push/tag/fallback branch never deploys.

      Open CI and manual workflow runs ↗
      You should see

      Exact-SHA job/artifact evidence, failed/skipped checks visible, and no cloud action inferred.

    DCopyable material

    Every command and message for this page sits inside its step, next to the explanation, with its own Copy button.

    EExpected result

    A scoped reviewed handoff with explicit publication permissions and actual current CI, without disturbing another session or the primary clone.

    FVerify and recover

    How to confirm success

    Confirm actual diff, authorization, target/source SHA and every required job outcome. Keep dated evidence distinct from current branch state or laptop acceptance.

    If something goes wrong

    Write/access/seat is unavailableDo not repeat
    Likely cause
    Separate account/entitlement prerequisite missing
    What to do
    Stop and use approved human/IT sign-in/access management; do not collect or substitute credentials.
    Hosted run belongs to another/stale SHASafe to repeat
    Likely cause
    Branch moved or recorded evidence is old
    What to do
    Inspect the intended exact commit and all job results; never treat a green branch label as source identity.
    Unrelated files appear staged or changedRepeat with care
    Likely cause
    Shared/unrelated work already exists
    What to do
    Preserve it and stage only intended files; do not reset/clean/stash blindly or amend history.

    Safe recovery

    Use a separate reviewed clean checkout when necessary. Keep historical demo-baseline unchanged and unsafe; inspect demo-complete only for the schedule fallback, never cloud dispatch.

    Limits of this check

    CI checks repository behavior/builds; it does not accept this laptop, user sign-in, live requests or environment reviewer protections.
