    Recover and retain

    Stopped-partial recovery and owned-output cleanup

    Recover without laptop rollback, broad uninstall or source loss. Stopped-partial setup, sample fallback and narrow owned-output cleanup are different decisions.

    Documented⏱ Stop and establish ownership/vendor state; no rushed recovery$ Retain shared tools and existing cloud resourcesWorkstation showcase

    Copy-only instructions. Checkmarks are manual progress, not laptop verification.

    !
    Separate human approval required. Cleanup/reset/repair/cloud actions remain human-only, never the setup agent. Named local Workstation setup may resume only after known vendor/reboot safety, fresh inventory and new scoped approvals; ordinary agents use source/mocks.

    APurpose and place in the demo

    Retain installed tools/settings/accounts/distro data and every unrelated source/editor change while resolving the actual blocker.

    Default cleanup is a nonmutating ownership plan, not a workstation uninstaller or demo-reset wrapper. Missing/ambiguous ownership never means permission to adopt or delete.

    BStarting state

    Identify the specific task/vendor/process and source checkout. Wait for setup/resume and app/test/Restore tasks to finish before suggesting clone update or cleanup. Save unsaved editor work.

    CExact actions

    1. YYou / IT

      Treat a force-closed legacy base as stopped partial

      Original setup outcome›IT/vendor review

      F
      Field note partial · Stopped partial is not success

      Do not use Finish/SkipBase after a stopped partial legacy base. Preserve tools, settings, accounts and distro data; establish vendor/reboot state and use reviewed installed-first inventory.

      Source-bound operating boundary; not a laptop observation.

      No automatic Finish/SkipBase, reboot/resume, restart, repair or rollback. Preserve everything already installed. Establish vendor/elevated-child and required/pending restart state before another module/download.

      Read known logs/state and actual final summary/flagged steps. A live PID, lock or log activity is not successful completion; do not force-clear a lock or blindly repeat installers.

      You should see

      Truthful stopped/failed/uncertain state and approved next decision, never success inferred from partial output.

    2. YYou / IT

      Retain state and inventory genuine missing targets

      Reviewed installed-first module source›Human decision

      Normal recovery is reviewed local installed-first inventory, not the broad legacy bundle. Compatible installed targets retain version/location/settings and skip before downloads; unknown/incompatible registered state is retained and stops.

      After vendor/reboot safety is known, the human may reselect Workstation setup and use its source-bound resume prompt for fresh inventory and new approvals. Ordinary agents cannot preview/apply; no agent repairs.

      Known Python/pwsh discovery can work despite stale VS Code PATH. Save and fully exit/reopen from Windows when needed; do not globally rewrite PATH/JAVA_HOME/profile/Copilot accounts or reset/update distros.

      You should see

      A narrow actual missing-target review, never blind retries, repair or inferred completion.

    3. YYou / IT

      Preserve all source and choose a safe prepared fallback

      Source Control›File: Open Folder›Separate reviewed checkout

      1. Stop agent edits and preserve staged, unstaged, untracked and unsaved work.
      2. Prefer a separately prepared reviewed clean main checkout or inspected demo-complete schedule fallback; never switch a dirty/shared/active checkout.
      3. Verify actual ref/content before human tests/launches. Historical demo-baseline is unsafe, never a run/reset/deployment source.
      4. Deployment from a fallback branch is forbidden. A user-approved sample reset is a separate explicit exercise, not routine cleanup.
      You should see

      A known safe source/fallback while all unrelated work and the historical tag remain retained.

    4. YYou / IT

      Preview narrow ownership only after tasks finish

      Terminal›Run Task›Cleanup preview

      Inspect newly recorded exact unchanged file identities/fingerprints. Shared tools/GHCP/extensions, accounts, environments/module/cache trees, source, logs outside the checkout, WSL/data and cloud resources are always retained.

      Agents validate cleanup with isolated fixtures/mocks only, never a real checkout even for the default plan. Missing/changed/ambiguous ownership retains; no adoption or repository-wide sweep.

      You should see

      A human-reviewed nonmutating exact ownership plan, not permission to remove a folder because it looks generated.

    5. YYou / IT

      Apply only separately confirmed exact owned outputs

      Terminal›Run Task›Cleanup generated resources

      Only after reviewing the plan, the human explicitly confirms exact unchanged newly owned files. Containers require separate exact immutable workspace-labelled ownership/opt-in, never name-based mass remove or prune.

      Do not delete .venv/.tools/target/HTML/cache trees, shared SDK/extensions/Copilot/accounts/distros, primary clone, Downloads contents, source, external logs or cloud resources. The committed companion is source, not a disposable cleanup tree.

      You should see

      Only exact positively owned unchanged authorized outputs removed; everything else retained.

    EExpected result

    The actual failure is surfaced while installed/shared state and unrelated work remain intact. Cleanup, sample reset, setup, Restore and deployment remain distinct approvals.

    FVerify and recover

    How to confirm success

    Inspect actual source status and the exact retained/eligible ownership plan. Verify vendor/restart uncertainty is resolved before any human retry. No laptop rollback or new baseline tag is assumed.

    If something goes wrong

    Timeout/cancelled installer may still be runningDo not repeat
    Likely cause
    Unknown vendor/elevated-child outcome
    What to do
    Pause further installers/downloads and establish the specific owned process/outcome with IT. No mass termination or blind retry.
    Cleanup sees missing/changed/ambiguous ownershipDo not repeat
    Likely cause
    Identity/fingerprint or original ownership cannot be proven
    What to do
    Retain it; do not adopt, recursively delete or relax the identity check.
    Primary clone/another session has unrelated workDo not repeat
    Likely cause
    Shared or active source surface
    What to do
    Do not update/reset/switch it. Save and retain work; use a separately reviewed prepared checkout.
    Unsafe baseline suggested as demo fallbackDo not repeat
    Likely cause
    Historical deliberate defects mistaken for safe source
    What to do
    Never run/reset/deploy it. Inspect revised main or the separate schedule fallback instead.

    Safe recovery

    Read-only inspection and source/mocks are permitted; state-changing actions require their distinct authorized human path. No blanket delete/reset --hard/clean/container prune, policy bypass, repair, auth or cloud mutation.

    Limits of this check

    This page did not run cleanup, reset, vendor repair, module preview/apply or inspect a live laptop's owned processes. Manual ticks are not retention/cleanup proof.
